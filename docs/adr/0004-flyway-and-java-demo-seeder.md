# 0004. Flyway migrations and a Java demo data seeder

- Status: Accepted
- Date: 2026-09-21

## Context and problem statement

The first versions let Hibernate generate the schema (`ddl-auto=create-drop`, later `update`) and inserted demo
data with `import-*.sql` scripts. The PostgreSQL profile lost its data on restart (later: schema changes were applied
implicitly and never reviewed), and fixed demo dates would make the v2 dashboard (last six months, 30-day alert
windows) look empty after a few weeks.

## Considered options

- Hibernate `ddl-auto` + `data.sql`
- Flyway (or Liquibase) for the schema; demo data as SQL migrations
- Flyway for the schema; demo data generated by a Java component at startup

## Decision outcome

Chosen option: **Flyway for the schema, a Java `DemoDataSeeder` for the demo data**.

- `src/main/resources/db/migration/V<n>__*.sql`, written in portable SQL that runs on PostgreSQL and on H2;
  Hibernate only validates (`ddl-auto=validate`).
- The seeder inserts 12 employees and 50 feedback items relative to the current date through the repository ports,
  only while the `employees` table is empty, so data survives restarts. It is enabled with `app.seed.demo-data`
  and off in the `prod` build. Feedback comes with a pre-set sentiment, so the dashboard works without a
  Hugging Face token.

### Consequences

- Good: schema changes are versioned and reviewed; the same migrations run in the H2 dev profile, the tests and on
  PostgreSQL (Testcontainers integration tests verify it).
- Good: the demo always shows a populated dashboard with a real alert, whatever day it is started.
- Bad: demo data is not a migration, so it is not part of the Flyway history; it is intentionally not meant for production.
- Bad: portable SQL rules out PostgreSQL-specific features until H2 support is dropped.
