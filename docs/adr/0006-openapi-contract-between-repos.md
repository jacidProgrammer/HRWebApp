# 0006. OpenAPI as the contract between the API and the UI repositories

- Status: Accepted
- Date: 2026-09-21

## Context and problem statement

The React UI ([HRWebApp-UI](https://github.com/jacidProgrammer/HRWebApp-UI)) lives in a separate repository.
Hand-written TypeScript types for the API drift silently: a renamed field compiles in both repositories and
breaks at runtime.

## Considered options

- Hand-written types in the UI, kept in sync by review
- A shared package with the types
- The API's OpenAPI document, committed to this repository, as the single contract; the UI generates its types from it

## Decision outcome

Chosen option: **committed OpenAPI document** at [`docs/openapi.json`](../openapi.json), generated by springdoc
from the running application.

- Controllers and DTOs carry the documentation (tags, summaries, error responses, nullable fields, enums, bearer JWT
  security scheme); response fields are marked required because the API always serialises them.
- `OpenApiContractTest` boots the application, fetches `/v3/api-docs` and fails the build when it differs from the
  committed file. After an intended change: `./mvnw -Pupdate-openapi test`, then commit the file with the code.
- The UI generates its types from
  `https://raw.githubusercontent.com/jacidProgrammer/HRWebApp/main/docs/openapi.json`.

### Consequences

- Good: every API change shows up as a reviewable diff of the contract in the same pull request.
- Good: the UI gets compile-time errors instead of runtime surprises when it regenerates its types.
- Bad: the UI follows `main`, so a breaking API change must be coordinated (or versioned) with a UI change.
- Neutral: the document's `info.version` (`OpenApiConfig.API_VERSION`) is bumped by hand with the Maven version.
